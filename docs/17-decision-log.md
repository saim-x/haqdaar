## ADR-001: Central Use Case - Cash-Relief Grant (Sahara Widow Support Grant)
- **Context:** Brief asks for one deep public task uniting the widow, shopkeeper, and helper personas.
- **Decision:** Build end-to-end widow benefit application → verification → decision → payment → anti-scam verification, with a second config-driven program (`Guzara Allowance`) proving multi-tenancy.
- **Rationale:** Directly exercises monetary cost-of-being-wrong, forged documents, messy registries, fake "relief payment" SMS, consent, and shared-phone helper workflows in one coherent narrative.

## ADR-002: LLM Proposes, Deterministic Policy Disposes
- **Context:** Temptation in AI hackathons to let an LLM decide eligibility and output a self-reported confidence score.
- **Decision:** Keep `app/engine/` 100 % pure Python with zero LLM calls; use LLMs/ML only for extraction, voice, OCR, scam scoring, and grounded RAG. Never implement `AUTO_REJECT`.
- **Rationale:** Guarantees deterministic replay (Digital Twin), verifiable rule hashes for auditors, calibrated threshold sweeps, immunity to prompt injection in decisions, and resilience if OpenAI fails during the live demo.

## ADR-003: Synchronous SQLAlchemy 2.0 + `psycopg` v3 (Over Async)
- **Context:** FastAPI supports both `async def` and sync `def` routes.
- **Decision:** Use synchronous SQLAlchemy 2.0 + `psycopg[binary]` in FastAPI `def` endpoints (executed in AnyIO threadpool).
- **Rationale:** Eliminates `MissingGreenlet` / detached-session / event-loop bugs across 7 parallel agents and integrates cleanly with Alembic, pytest, OpenCV, and scikit-learn.

## ADR-004: PostgreSQL `SKIP LOCKED` Job Queue (Over Celery + Redis)
- **Context:** Case processing, payments, RAG re-indexing, and mock-outage retries require background jobs.
- **Decision:** Store jobs in a PostgreSQL `jobs` table claimed via `SELECT ... FOR UPDATE SKIP LOCKED` by `app/jobs/worker.py` (with optional `RUN_EMBEDDED_WORKER=true` for simple single-container deploy).
- **Rationale:** Transactional enqueue in the same commit as case submit (zero lost jobs), zero Redis dependency to deploy or debug, and native Admin Jobs UI directly over the table.

## ADR-005: React 18 + Vite PWA With Route-Split Bundles (Over Next.js)
- **Context:** Challenge 07 requires true offline support and tiny pages for weak connections, while Staff Consoles need rich dashboards.
- **Decision:** Single Vite React TypeScript app with `vite-plugin-pwa` (Workbox) and `React.lazy` route splitting isolating `/staff/*`, `/admin/*`, `/auditor/*` from the ≤ 150 KB gzipped Citizen/Helper PWA bundle.
- **Rationale:** Clean offline app-shell caching without Next.js SSR/RSC hydration failures; smaller citizen JS footprint; single-origin static serving from FastAPI eliminates CORS/SameSite friction.

## ADR-006: Hybrid Postgres `tsvector` + NumPy Cosine RAG (Over `pgvector`/Chroma)
- **Context:** Need grounded RAG over ~5–15 policy documents (~150–400 chunks) without deployment fragility.
- **Decision:** Store embeddings in standard PostgreSQL `DOUBLE PRECISION[]` alongside `TSVECTOR` and compute hybrid ranking in Python/NumPy (< 15 ms).
- **Rationale:** Works out-of-the-box on every managed Postgres (Neon/Supabase/Docker) with zero custom extensions or external vector DB services.

## ADR-007: Signed-QR + OpenCV + OCR Document Verification (Over Tesseract-Only)
- **Context:** Document forgery detection (Challenge 08) must catch edited names without falsely accusing genuine WhatsApp-compressed photos.
- **Decision:** Use OpenCV Laplacian blur (`NEEDS_RETAKE`), `cv2.QRCodeDetector` + `HMAC-SHA256` signature check, and printed-text OCR cross-check against QR payload (`TAMPER_SUSPECTED`). Missing QR or low quality degrades to `UNVERIFIABLE` / `NEEDS_RETAKE`.
- **Rationale:** Avoids flaky OS binary installs (`tesseract`/`libzbar`), achieves `0 %` false-tamper rate on compressed genuine cards, and demonstrates cryptographic + AI defense-in-depth.

## ADR-008: Isolated DB Session for Denied Consent Access Logging
- **Context:** Raising HTTP `403 CONSENT_REVOKED` inside a FastAPI request normally triggers a SQLAlchemy transaction rollback, which would erase the `consent_access_logs` entry.
- **Decision:** `enforce_consent()` persists denied access rows and `consent.access_denied` audit events using a separate short-lived `SessionLocal()` commit before raising `ConsentRevokedError`.
- **Rationale:** Guarantees citizens and auditors immediately see blocked access attempts (Challenge 06).

## ADR-009: `AI_PROVIDER=live|fake` Dual Mode & Pre-Generated Static Urdu Prompts
- **Context:** Live demos can suffer OpenAI rate limits, latency spikes, or venue Wi-Fi issues; CI tests must be fast and free.
- **Decision:** Pre-generate ~45 static Urdu MP3 prompts (`ur-PK-UzmaNeural`) cached in the PWA; route all dynamic AI calls through `AIProvider` with automatic fallback to `FakeDeterministicProvider` and deterministic rule-template explanations.
- **Rationale:** Zero-latency offline audio for citizens, < 45 s deterministic CI tests, and an unbreakable live demo.

## ADR-010: Single Database With Strict Import Boundary for Mock DPI Services
- **Context:** Brief requires clean APIs for mock identity/payment/data services and a fast demo reset.
- **Decision:** Store `mock_*` tables in the same PostgreSQL instance for atomic `< 5 s` demo reset, but enforce via `test_invariants.py` that `app/api/`, `app/engine/`, and `app/agent/` NEVER import `app/mocks/` and call `/mock/v1/*` strictly over HTTP (`httpx`).
- **Rationale:** Full architectural separation + authentic HTTP chaos testing without managing a second database.

## ADR-017: Given-Name Protection in Name-Similarity Checks (Shared-Surname Populations)
- **Context:** DPI's evaluation set exposed that full-string token-set similarity lets a Photoshopped **given** name pass a 0.80 threshold whenever the surname is shared - the demo population heavily shares "Bibi" ("Zainab Bibi" vs "Sakina Bibi" = 0.818 on full string).
- **Decision (approved):** DPI's `doc_verify` printed-vs-QR cross-check uses `min(full_name_ratio, given_name_ratio)` after honorific stripping (verified samples: Zainab/Sakina 0.667, Fatima/Fatima 1.0, Mst. Fatima/Fatima 1.0, Muhammad/Mohammad Akram 0.875). EN evaluates adding the same guard to `entity_resolution.name_sim` adopted **iff** the full 25+ case regression suite stays green (golden path must remain 1.0). Also recorded: scam classifier adds `MIN_MEANINGFUL_WORDS = 5` alongside the spec's `< 15 chars` rule so "Bhai payment bhej dena" resolves to `CANNOT_TELL` per demo scene 3; RAG fake-mode embeddings are 64-dim per docs/04 §4.5 and `cosine` returns 0.0 (not truncated) on dimension mismatch.
- **Rationale:** Tamper and identity-jacking protection for a surname-colliding population; conservative direction - can only increase human review, never auto-approvals.

## ADR-018: Audio Prompt Registry - Canonical Manifest Shape and Key Names
- **Context:** FE (consumer) and DPI (producer) independently invented disjoint key names for the same Urdu prompts (FE `wizard_applicant_full_name`… vs DPI `step_full_name`…), and DPI shipped `manifest.json` as an envelope (`{voice, voice_alt, language, count, keys, files}`) while the pinned contract was a top-level `{key: text}` map. ## ADR-020: `GET /me/data` Emits the docs/04 §5 Tri-State, and Reads the Flat `profile_data`
- **Context:** Two defects in the citizen self-data view, found while auditing the Urdu UI. (a) `me.py` built `household` from `profile_data["household"]`, a nested key the seed never writes - `profile_data` is flat, with the canonical fact keys directly on it - so **every** citizen's household came back `{}`. An empty household is not a neutral answer: it reads as "we hold nothing about you", the opposite of the truth for a seeded citizen. The existing test only asserted the group *existed*, which an empty dict satisfies. (b) `MyDataValue` was `{value, source}`, so the frontend inferred "unknown" from `value === null`. That is the tri-state invariant (AGENTS.md §3.3) being reconstructed on the client from a null, which is exactly the coercion the invariant forbids - and it cannot distinguish "you have not told us" from "a government service was down".
- **Decision (Integration Lead):** `GET /me/data` returns every `identity` and `household` value in the docs/04 §5 fact shape: `{state, value, source, missing_reason}`. `state` is strictly `KNOWN`/`UNKNOWN`; a `KNOWN` value carries a `source` and a null `missing_reason`, an `UNKNOWN` value carries null `value`/`source` and a `missing_reason` from `app.engine.facts.MissingReason`. Every canonical household key is emitted whether or not it is held, so a missing fact is stated rather than omitted. `household` is read from the flat `profile_data` keys. The frontend reads `state` and renders the reason; it no longer infers anything from `null`.
- **Rationale:** Restores the invariant at the boundary that owns it. The shape is the same one `decisions.input_snapshot_json` already uses, so there is one fact representation in the system rather than two. Additive for existing consumers: `value` and `source` keep their names and positions, and `source` becomes nullable only where it was already meaningless.

## ADR-022: RAG Chunks Are One Section, and Abstention Adds a Corpus-Coverage Gate
- **Context:** Two defects found by asking the live `/rag/ask` endpoint real questions. (a) `CHUNK_MIN_TOKENS = 300` merged two or three policy sections per chunk, and `CHUNK_OVERLAP_TOKENS = 50` prepended the previous chunk's tail to every chunk - so the chunk titled "3. Required Documents" opened with the tail of the eligibility list in Urdu. The heading stopped describing the content, and an extractive answer quoted the neighbour's text under this section's citation. (b) The abstention gate was a similarity threshold alone, so "what is the weather in Karachi tomorrow?" was answered: Karachi is a district in the eligibility list, one word of three matched, and the cosine cleared the bar.
- **Decision (Integration Lead):** `CHUNK_MIN_TOKENS` 300 → 60 and `CHUNK_OVERLAP_TOKENS` 50 → 0, so a chunk is exactly one section and its heading describes all of it. `rag.ask` gains a second, independent gate: `_corpus_coverage(question)` is the share of the question's content words that appear anywhere in the corpus, and below `MIN_CORPUS_COVERAGE = 0.5` the answer is `NOT_SURE` whatever the similarity score. `RagAnswer.coverage` is exposed in `POST /rag/ask` (docs/05 updated) so an abstention can be explained. The extractive answerer quotes one whole paragraph from one source, joins a lead-in ending in `:` to the list it introduces, and answers in the language that was asked.
- **Rationale:** A citation names a section, so a section is the unit a chunk must hold - otherwise the citation is a lie even when the retrieval score is high. Coverage and similarity answer different questions ("is this about our corpus?" vs "is some chunk similar?"), and only coverage is stable when chunk sizes change; measured over the corpus, in-domain questions cover 0.67–1.00 of their content words and off-topic ones 0.00–0.33.

## ADR-024: Urdu Renders in Nastaliq, and the Subset Keeps the Joining Features
- **Context:** Every Urdu string in the UI rendered letter-by-letter - "پروٹوٹائپ ڈیمو لاگ ان" came out as isolated glyphs, unreadable as a word. Root cause was in `frontend/scripts/build-fonts.py`: `Options.layout_features` listed only `kern, liga, calt, mark, mkmk, rlig`, so the subsetter dropped the Arabic contextual-joining features `init`/`medi`/`fina`/`isol`. The shipped `NotoSansArabic-subset.woff2` therefore carried `rlig` alone, and every letter could only ever take its isolated form. Nothing errored - the font loaded, the glyphs drew, the text was simply wrong. Verified by shaping the string with HarfBuzz: the old face moved 5.7 px between shaped and unshaped layout (mark positioning only), the corrected face 251.9 px (real ligature joining). Separately, the face was `Noto Sans Arabic`, a Naskh design that reads as Arabic rather than Urdu.
- **Decision (user-approved):** The Urdu face becomes **`Noto Nastaliq Urdu`** (variable `wght` 400–700, subset to the Arabic block + supplement, 194 KB WOFF2). `build-fonts.py` now lists `ccmp, locl, init, medi, fina, isol, rlig, rclt, calt, liga, mark, mkmk, curs, kern` explicitly. The type scale's leading moves to CSS variables (`--lh-*`) so `html[lang='ur']` - set by `I18nProvider` - claims ~1.9 leading for Nastaliq while the English UI keeps the tighter Latin rhythm. No component changed.
- **Rationale:** Nastaliq is the script Urdu is actually written in; its sloped baseline and stacked ligatures are what make a word read as a word. The joining features are not optional decoration - omitting them is a silent correctness bug, so they are now named explicitly in the build script rather than inherited from a default. The leading is scoped to `lang='ur'` because Nastaliq's descenders sit far below the baseline and would otherwise collide with the next line's marks. Cost: the Urdu face grows 26 KB → 194 KB, which is inherent to Nastaliq (a glyph per positional form and per common ligature) and does not count against the 150 KB JS budget; the gate still passes at 131.2 KB.
- **Supersedes:** A parallel fix for the same joining bug landed on `main` first, keeping `Noto Sans Arabic` and widening `layout_features` to `["*"]`. That fixed the correctness defect but left the face as Naskh. This ADR keeps the correctness fix (the joining features are now named explicitly, and `subset(..., preserve_shaping=True)` is the only path that can produce the Urdu face) and changes the design to Nastaliq. `NotoSansArabic-subset.woff2` is removed; nothing else referenced it.

## ADR-025: Bandwidth-Aware Interactive Video Guide (Anam.ai Audio Passthrough)

- **Context:** The citizen PWA is Urdu-first and voice-first, but a low-literacy citizen still has to read the answer, the decision reasons, and the wizard prompts. A talking guide is the accessibility feature that closes that gap, and a photorealistic one is what makes the demo land. The obvious implementation - hand the conversation to the avatar vendor's own LLM - would break three invariants at once: the avatar would answer policy questions from its own weights (hallucination), it would need the citizen's question and case context (PII egress), and it would be a second, unaudited decision surface. The vendor's free tier is also 30 min/month, 3 min/session, 1 concurrent session, so an auto-connecting player would burn the demo budget on page loads.
- **Decision (user-approved):**
  1. **Audio passthrough, not vendor conversation.** `ANAM_MODE=passthrough` (default) requests a session token with `personaConfig.enableAudioPassthrough: true`; the browser decodes our own Deepgram Flux `flux-ambreen-ur` audio (the 73 pre-cached `/audio/ur/*.mp3` prompts and dynamic `POST /voice/tts` clips) to 24 kHz mono `pcm_s16le` via `AudioContext.decodeAudioData` + `OfflineAudioContext` and streams it to the avatar. The avatar is a **mouth**, never a mind: it receives audio, never text, never a question, never a case. `ANAM_MODE=talk` (`llmId: CUSTOMER_CLIENT_V1`, `skipGreeting: true`) exists as a single-env-toggle fallback and is not the default.
  2. **The guide is grounded or silent.** Spoken policy answers come from `POST /rag/ask` with the additive `conversational: true` flag, which adds a `spoken_summary` (≤ 280 chars) derived from the single retrieved citation chunk. `answer` and `citations` are returned verbatim and unchanged. On `NOT_SURE` the summary is a fixed warm abstention sentence and **no model is called**.
  3. **Credit discipline is a product requirement.** No WebRTC connection without an explicit tap; 90 s idle auto-disconnect; 165 s soft cap (below the vendor's 180 s) with a 20 s warning and a one-tap renew; `stopStreaming()` on unmount, route change and `visibilitychange`. `AI_PROVIDER=fake` serves a full local simulator (animated guide + real `<audio>` playback) so every test, CI run and Playwright spec consumes **0.0 streaming minutes**. `backend/scripts/verify_anam.py` proves live credentials with `GET /v1/avatars` + `POST /v1/auth/session-token` only - token issuance is not billed.
  4. **Lazy isolation.** `@anam-ai/js-sdk` is imported only inside `connect()` in live mode, behind `React.lazy()`. It must never appear in `dist/index.html`, so the ≤ 150 KB citizen initial-JS gate keeps its meaning.
  5. **Bandwidth step-down is the feature, not the fallback.** `LiteModeProvider` (`saveData` / `2g` / `slow-2g`) or an offline browser replaces the video with an audio-only companion strip over the same cached MP3s. Challenge 07 asks for graceful degradation; this is where it is visible.
  6. **Graceful provider failure.** Any Anam HTTP error, timeout or quota exhaustion returns `200` with `{ available: false, fallback: "AUDIO_ONLY", reason: "PROVIDER_UNAVAILABLE" }` and a bilingual message, and records `ai_telemetry`. A vendor outage must not become a 500 on a citizen screen.
- **Rationale:** The avatar is the most expensive and least trustworthy component in the system, so it is given the smallest possible job: render a face and move its mouth to audio we already produced and already trust. Everything that decides anything stays in `app/engine/`, and everything that speaks policy stays in `app/ai/rag.py`. The free-tier limits are treated as design constraints rather than an operational risk, which is why the zero-credit simulator is the default in every non-live environment.
- **Contract:** `GET /api/v1/avatar/config` (any authenticated) and `POST /api/v1/avatar/session` (CITIZEN/HELPER, 10 sessions / 10 min per user) are documented in docs/05 §3.9. `POST /rag/ask` gains the optional `conversational` request field and the optional `spoken_summary` response field; both default off, so no existing caller or test changes.

### ADR-025 Amendment 1 (Round 2): `conversational` Becomes the Live Default

- **Context:** Round 1 shipped `passthrough` as the default, which makes the avatar a mouth and nothing else. That is the safest possible design, but it is not the product: a low-literacy citizen cannot read a policy answer, and the whole point of a talking guide is that she can *ask* - "السلام علیکم، میرا شوہر فوت ہو گیا، مجھے مدد چاہیے" - and be understood. `passthrough` also has a hard operational dependency: it needs `DEEPGRAM_API_KEY` and `OPENAI_API_KEY` for STT/TTS, and both are empty in the demo environment. A guide that cannot hear is a video, not a conversation.
- **Decision (user-approved):**
  1. **`ANAM_MODE=conversational` is the new default.** The session token is requested with a `personaConfig` carrying `avatarId`, `llmId`, `voiceId`, `languageCode`, `name`, `systemPrompt` and `maxSessionLengthSeconds`. The client calls `createClient(token, { disableInputAudio: false })` so the vendor captures the citizen's microphone over WebRTC with its own VAD and barge-in, and `client.talk()` / `client.sendUserMessage()` drive Saima's replies. `passthrough` and `talk` remain fully wired and are one env var away.
  2. **The prompt is built from the live rule set, not from a constant.** `build_saima_system_prompt(db, surface, lang)` reads the active `rule_versions` row (falling back to `policy_docs`) and injects the current income cap, base amount, per-child bonus, hard cap, required documents and the `HQ-XXXXX` verification scheme. Publishing rule v2 changes what Saima says on her next session, with no deploy. The prompt carries **zero citizen PII** - no CNIC, no phone, no name, no case record - and states the three hard guardrails: never decide eligibility, never ask for CNIC/OTP/PIN/fee, and abstain honestly on anything outside Haqdaar.
  3. **The vendor's LLM is a mouth with ears, still not a mind.** It never sees a case, never sees a decision, and never produces a citation. Grounding stays where it was: the citizen's typed or spoken policy question is *also* sent to `POST /rag/ask` in the background, and if the corpus matches, the verifiable citation chip appears on the stage next to the spoken answer. Two channels, one truth: the voice is warm, the chip is checkable.
  4. **Test context always wins.** `_is_fake_mode()` returns `fake` whenever `APP_ENV=test` or `PYTEST_CURRENT_TEST` is set, regardless of keys, so pytest and CI can never spend a streaming minute. Outside tests, `ANAM_ALLOW_LIVE_IN_FAKE_AI` (default `true`) lets a developer run the **real** avatar against `AI_PROVIDER=fake` - the two providers are independent, and conflating them was the bug that made the live avatar unreachable in the demo environment. Playwright is protected separately by `src/e2e/global-setup.ts`, which aborts the run if `/avatar/config` reports `provider: "anam"`.
  5. **Discovery is cached and permissive.** `resolve_avatar_id()`, `resolve_voice_id()` and `resolve_llm_id()` each query their catalogue once per process and cache. Blank ids are omitted from `personaConfig` rather than sent as empty strings, because the live API accepts unknown fields but a blank `voiceId` is a different thing from an absent one.
- **Known limitation, stated plainly:** Anam's public voice catalogue (1,437 voices) contains **no Urdu voice** - the closest are 59 `hi` voices, and the account's own 10 voices are all `en`. `resolve_voice_id()` therefore prefers `ur`, then `hi`, then a warm female name, then any female voice, and the demo account resolves to *Amanda - Warm Guide*. Conversational mode is a warm English-accented voice reading Urdu text; pronunciation quality is **unverified** and is the first thing the manual test script asks the user to judge. `passthrough` remains the authentic-Urdu path (Deepgram Flux `flux-ambreen-ur`) and is the recommended mode once `DEEPGRAM_API_KEY` and `OPENAI_API_KEY` are set.
- **Rationale:** The citizen's ability to speak is worth more than the vendor's accent. A warm voice that occasionally mispronounces a word still lets an illiterate citizen ask her question out loud, which is the accessibility claim the product makes; a perfect accent behind a text box does not. The guardrails are unchanged in kind - the avatar still cannot decide, still cannot see PII, and still cannot invent a citation - so the risk this amendment adds is confined to pronunciation, which is a quality issue, not a correctness one.
- **Contract:** `GET /api/v1/avatar/config` gains `conversational: bool` and reports `mode` from the three-value enum. `POST /api/v1/avatar/session` returns `conversational` alongside `mode`. No existing field changed meaning; `passthrough` and `talk` callers see identical payloads to Round 1.

### ADR-025 Amendment 2 (Round 3): `home` Becomes a Guide Surface

- **Context:** The guide was reachable only from inside "Ask a question", which is the wrong door for the citizen it exists for. A low-literacy citizen does not arrive with a policy question; she arrives not knowing which of four tiles applies to her. Burying the one voice-first surface one level down meant the accessibility feature was only discoverable by people who could already read the menu. The home screen is where the guide belongs, and it needs its own `surface` value so the audit trail records where a session actually started rather than mislabelling it `ask`.
- **Decision (user-approved):**
  1. **`home` joins the surface enum.** `SURFACES` becomes `{ask, case_status, wizard, scam_check, home}` and `_SURFACE_HINT["home"]` tells the prompt the citizen "has not chosen a task yet", so Saima opens by offering the four things she can do rather than assuming a policy question.
  2. **The home page gets a hero tile, not a fifth row.** `AvatarHero` renders the portrait, the persona name, one sentence and a 56 px button. It is a *different invitation*, not a second state machine: once tapped it hands off to `AvatarToggleCard`, which still owns the stage, the audio-only fallback and the lazy WebRTC chunk. The session lifecycle exists in exactly one place.
  3. **The portrait moves out of the lazy chunk.** `GuideFace` and `MOOD` are extracted to `shared/avatar/GuideFace.tsx` so the entry bundle can draw the guide without importing `AvatarStage`. `@anam-ai/js-sdk` still never appears in `dist/index.html`; the ≤ 150 KB gate keeps its meaning.
  4. **The four support rows become a 2×2 bento grid.** The guide is promoted out of the list, so the list no longer has to carry it. Every tile keeps its own 48 px listen affordance (docs/11 §2.2), which is why the audio button sits in a footer strip rather than floating over the link.
- **Rationale:** The guide is the product's accessibility claim, and an accessibility feature that requires reading a menu to find is not one. Promoting it costs one additive enum value and no new dependency; the alternative - reusing `surface: "ask"` from the home screen - would have written a false value into the audit chain, which is the one thing this system does not do.
- **Contract:** `POST /api/v1/avatar/session` accepts a fifth `surface` value, `home`. Additive only: the four existing values, every response field and every status code are unchanged, so no existing caller or test changes.

## ADR-026: Documentation Tracks What Shipped - Render + Neon, and a Vendor-Neutral AI Provider

- **Context:** Two frozen documents described a system that was never deployed. (a) `03 §2` and `03 §6.5` specified a Railway project with three services and a shared Railway volume, but the shipped deployment is a single Render Docker web service (`render.yaml`) with `RUN_EMBEDDED_WORKER=true` and a Neon managed PostgreSQL 16 database. The same stale reference appeared in `01`, `02`, `12`, `14`, `16` and `17`. (b) `03 §2` and `07 §1` described the live AI layer as calling OpenAI `gpt-4o-mini` / `whisper-1` / `text-embedding-3-small` plus `edge-tts`, but the live path calls Deepgram Nova-3 for speech-to-text and Deepgram Flux for speech synthesis, and the deployed gateway is Mistral (`mistral-small-latest` / `mistral-embed`) through `OPENAI_BASE_URL`. `whisper-1` and `edge-tts` survive only as a config default and a cost-table row. A judge reading the docs and then the repository would find the docs wrong on the two facts most likely to be checked.
- **Decision (user-approved):** Correct the documents to match the shipped system rather than change the system to match the documents. Deployment is documented as Docker Compose (local) + Render (cloud) + Neon (managed Postgres), with Railway recorded as a planned-but-unused alternative. The AI layer is documented as an OpenAI-compatible `AIProvider` whose vendor is a configuration value, naming the default models and the demo gateway models explicitly, and naming Deepgram Nova-3 / Flux as the actual speech path with `edge-tts` as the fallback. No code, schema, API contract, canonical fact key or routing threshold changes.
- **Rationale:** The frozen docs were written before deployment was attempted, and the deployment target changed for a real reason: Render's blueprint plus Neon needs one container and no second service, which is what the free plan allows. The AI vendor changed for a different real reason: the provider was built against the OpenAI SDK, so pointing `OPENAI_BASE_URL` at an OpenAI-compatible gateway is a config change, not a rewrite. Both are defensible decisions that read as inconsistencies only because the docs were never updated. A prototype whose central claim is "the audit trail never lies" cannot ship documentation that does.
- **Contract:** None. Documentation only - `01`, `02`, `03`, `07`, `12`, `14`, `16`, `17`. No migration, no endpoint, no response field, no test changes.
